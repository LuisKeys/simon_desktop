# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Simon Desktop (module `simondesktop`) is a Wails v2 desktop app: a Go backend wrapping the
`github.com/LuisKeys/simon` agent runtime, with a React/TypeScript frontend. It's a personal
document assistant — chat UI backed by an LLM agent runtime that supports OpenAI, Anthropic, and
Ollama providers.

## Commands

Backend (Go), from the repo root:
- `go build .` — build the backend
- `go test ./...` — run all Go tests
- `go test ./internal/sessions/... -run TestGetOrCreateReusesSessionPerConversation` — run a single test
- `go vet ./...`

Frontend, from `frontend/`:
- `npm install`
- `npm run dev` — Vite dev server
- `npm run build` — `tsc` type-check then `vite build` (output feeds the Go embed in `main.go`)

Full app:
- `wails dev` — live dev mode (hot-reloads frontend; also serves a devtools-connectable server at
  http://localhost:34115)
- `wails build` — production build

There is no lint script configured for the frontend.

## Architecture

**Process boundary.** `main.go` embeds `frontend/dist` and binds a single `app.AppService`
(`internal/app/app.go`) to Wails as the RPC facade the frontend calls into
(`frontend/wailsjs/go/app/AppService` — generated by Wails, do not hand-edit). Wails also
generates `frontend/wailsjs/go/models` from the Go structs returned across the boundary; if you
change field shapes on `Conversation`, `ChatMessage`, or the `Chat*Event` types, regenerate
bindings rather than hand-editing the wailsjs output.

**Two persistence stores, deliberately separate:**
- `internal/persistence` (SQLite via `modernc.org/sqlite`, no cgo) holds only conversation
  *metadata* (`conversations` table: id/title/timestamps) plus `documents` and `settings` tables
  reserved for future phases.
- Actual message content lives in Simon's own per-session JSON memory files, one per conversation,
  under `paths.ChatsDir` (`~/Library/Application Support/SimonDesktop/chats/<conversationID>.json`).
  `internal/sessions/history.go` reads this directly via `memory.NewJSONFileIn` to reconstruct chat
  history for the frontend — it does not go through the SQLite layer at all.

This split means conversation *list/title* operations (`internal/conversations`) and conversation
*content* operations (`internal/sessions`) are independent; don't conflate them when adding
features that touch conversation state.

**Session lifecycle.** `internal/sessions.Manager` maintains one `simon.Session` per conversation
ID for the life of the process (created lazily via `GetOrCreate`, never explicitly removed —
`simon.Runtime.Close()` closes every session it created, called from `AppService.Shutdown`). Every
session is created with the same `SystemPrompt` constant. There's no session eviction; long-running
processes accumulate one live session per conversation ever opened.

**Async run flow (the core request pattern):**
1. Frontend calls `SendMessage(conversationID, text)` — returns immediately once the run has
   *started*, not once it finishes.
2. `AppService.SendMessage` gets/creates the session, calls `sess.Stream(...)` to get a
   `<-chan simon.Event`, records the message in SQLite metadata (bumps `updated_at`, derives a
   title from the first message), then hands the channel to `consumeRun` in a goroutine.
3. `consumeRun` translates `simon.Event`s into stable, frontend-facing Wails events defined in
   `internal/app/events.go` (`chat.run.started/completed/failed/cancelled`) via
   `wailsruntime.EventsEmit`.
4. The frontend (`Chat.tsx`) subscribes with `EventsOn` and updates UI state per conversation ID
   from event payloads — it does not poll or await a long-lived call.

Cancellation follows the same shape: `CancelRun` looks up the session (does not create one) and
calls `sess.Cancel()`; the resulting `EventRunCancelled` flows through the same event channel.

**Error handling boundary.** `internal/app/errors.go` centralizes translation from internal errors
(`simonerr` sentinel errors, or best-effort keyword matching on the string from a `run.failed`
event's data) into the small set of user-facing strings the UI actually renders. Add new
user-facing error cases here, not inline in `app.go` or the frontend.

**Frontend event contract.** The `chat.run.*` event names and payload shapes in
`internal/app/events.go` are treated as a stable interface with the frontend's `EventsOn` listeners
in `Chat.tsx` — don't rename without updating both sides in the same change.

## Configuration

Provider credentials are read from `.env` (see `.env.example`): `OPENAI_API_KEY`/`OPENAI_MODEL`,
`ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL`, `OLLAMA_HOST`/`OLLAMA_MODEL`, and `DEFAULT_MODEL`
(`auto` or an explicit model id). At least one provider must be configured or runs fail with the
"No model provider is configured." friendly error. `EMBEDDING_PROVIDER`/`EMBEDDING_MODEL` configure
document-indexing embeddings (reserved for a later phase — `documents`/`settings` tables already
exist for this).

## Platform notes

`internal/platform/paths.go` currently hardcodes the macOS Application Support path
(`~/Library/Application Support/SimonDesktop`) as the root for the DB, chat memory, knowledge, and
attachments directories — there is no Windows/Linux equivalent yet.
